## Question

How does a tool that has to sign in somewhere, such as a browser, get a stored login or a one-off code from the owner, and how much of either does the model see?

Raised by Tim on 2026-11-14, after "Storage on the data volume" (TIM-536) closed: chad needs built-in credential tools, so that something like a browser tool has a way to store login credentials and to enter one-off OTP codes. That is all he has said. Nothing below the next heading is agreed for this ticket.

"Skills and MCP servers: where they live and how chad adds one" (TIM-537) closed on 2026-11-14 with its three rounds as agreed, so the points below from it are settled.

What other tickets hand it:

- "The chad CLI: what it covers and how it reaches the running daemon" (TIM-542): `chad secret set <NAME>` takes a value from stdin or a hidden prompt, `list` prints names, `rm` deletes, and there is no `get`. The agent may run all three. Named secrets are stored in `secrets/secrets.json`, mode 0600. A changed secret reloads the plugins and MCP servers that name it. The agent can read a secret file if it goes looking and v1 does not stop it, because clanka's `readFile` runs inside the daemon. chad sets `CHAD_SESSION=<session id>` on every process a session starts, so a command can tell which session ran it.
- "Skills and MCP servers: where they live and how chad adds one" (TIM-537): `${NAME}` in `mcp.json` resolves in chad's secret store first and then process env. An MCP OAuth login ends with the owner pasting a URL into the thread, and chad consumes that message by matching its `state` value, so it never reaches the model or the history. That is the one existing case of an owner message kept out of a session.
- "Storage on the data volume" (TIM-536): secrets are files under `secrets/` on the volume, outside the repo and the SQLite file. A session's history is in `session_messages`, kept until 30 days after a reset, and `chad backup` copies both.
- "Sessions and turns" (TIM-532): an owner message sent during a running turn steers it and is stored in the history. So a code typed as a plain message is in the history and in the database.
- "What a turn looks like in Discord" (TIM-533): the status message shows each script the agent runs as its truncated source. clanka's agent works by writing scripts, so a password written into a script shows in Discord and stays in the history. v1 has one Stop button and no other buttons or selects. The Discord adapter can show buttons, selects and modals, and what is typed into a modal is not a channel message.
- "Plugin API: what a plugin exports and what it can do" (TIM-530): a plugin reads its own secrets with `Config.Redacted`. The API has no call that asks the owner something and waits for the answer.
- The map names no browser tool. The agreed v1 features beyond clanka are scheduled tasks and sessions that survive a restart, so this ticket adds to v1.

Decide:

- Which tools use this in v1. If chad ships no browser, decide whether the credential tools ship ahead of one, and whether the browser arrives as an MCP server, a skill or a bundled plugin. A browser in the image is a decision for "Docker image and data volume layout" (TIM-541).
- What a stored login is: a name with a username, a password and the site it belongs to, or plain named secrets in the store the CLI ticket settles. Whether it can hold a TOTP seed, so chad makes the code itself and the owner is only asked for codes sent by SMS or email.
- Who saves a login and how: the owner through the CLI, the owner in chat, or the agent after the owner gives it one.
- Whether the model ever sees a password. The alternative is a tool that takes the login's name and the place to put it and fills the value in without returning it. That needs the tool that does the typing to resolve the name itself, so it shapes how a browser tool is built.
- How the owner gives a one-off code: a reply in the thread that chad takes out of the session, a Discord modal behind a button, or the CLI. How long the tool waits, and what the turn does on a timeout.
- What happens when a turn with no owner present needs a code, such as a cron job's turn. "Model provider and headless login" (TIM-535) has the matching rule for model logins: such a turn never starts one and ends with a notice.
- Whether these are core tools, a bundled plugin or a skill. As a plugin they need an API call that asks the owner and waits, and a way to reach secrets beyond the plugin's own. Either is a gap in the plugin API to raise here.
- What keeps a value out of the history, the status message, the logs and the `turns` table when a tool has handled it.
- Whether a site's login is open to every session, or only to the session that the owner gave it to.
