### Decided

Scope:

1. v1 ships the credential tools and no browser. chad supplies no browser as an MCP server, a skill or a bundled plugin. The owner adds Playwright MCP through `mcp.json`, or agent-browser as a CLI on the volume, against a Chromium sidecar over CDP or a derived image.
2. The promise: a stored value stays off the normal path. It is not in a script's source, not in an owner message, and not in what a chad command prints, except that `chad secret code` prints a code. chad does not promise it against an agent that goes looking, and a browser that has typed a password can be asked for it. `chad secret run -- printenv` prints a value, so the promise leans on masking, and the spec says so.
3. chad holds both factors when the owner stores a TOTP seed next to a password. Anyone who gets into the container has both. The spec says this in plain words as the owner's trade.

The store:

4. A login is plain named secrets in `secrets/secrets.json`, plus a `totp` kind. `chad secret set NAME --totp` takes base32 or an `otpauth://` URI and refuses what does not decode. 6 digits, SHA-1 and 30 seconds unless the URI says otherwise.
5. `chad secret set` gains `--note`, which by convention holds the site and the username. `chad secret list` prints name, kind, note and date. `set` on an existing name replaces the value and the kind and says so. It warns when a value is under 8 characters and so will not be masked.
6. No site binding in chad. Every session, sub-agent and background task can use every secret.

Getting a value to a tool:

7. `chad secret run --env VAR=NAME [--stdin NAME] -- <command>` runs the command with the secrets in its environment, or one on its stdin with no trailing newline and stdin then closed. The CLI reads `secrets/secrets.json` itself, daemon or not. A missing name exits 125 with the message on stderr, and the child's own exit code passes through otherwise. The agent may run it. There is still no `get`.
8. `chad secret code NAME` prints the current code and the seconds left, and is refused for a secret that is not TOTP. `run` gives a TOTP secret's current code in place of its seed. With under 5 seconds left in the window both wait for the next one. `${NAME}` naming a TOTP secret in `mcp.json` or `chad.json` fails the apply, and `chad secret set NAME --totp` is refused while the live `mcp.json` or `chad.json` names NAME.

Asking the owner:

9. `chad secret request NAME [--totp] [--note] [-m "<why>"]` posts a message with an Enter button in the session's thread. An owner's click opens a modal with one text field. The submit takes the same path as `chad secret set` through the daemon's queue, so what names the secret reloads. The message is then edited to "Saved NAME" and the button removed. The button's id carries the name and the kind, and clicks from anyone who is not an owner are ignored. A request for a name that already exists is allowed, since a wrong password is the usual reason for one.
10. The message reads as the agent asking: it names the session and quotes `-m` as the agent's words. The skill says to request only for a site the owner named in that session. This is the answer to a web page that tells the agent to ask for a bank password.
11. `chad secret request --code -m "<why>"` posts the same button, waits, and prints what the owner typed on stdout. Nothing is stored and the code is not masked. After the submit the message is edited to "Code received". This is how an SMS code, an email code or "type anything once you approved it on your phone" reaches a script without a new turn. An ordinary reply stays the fallback.
12. Waiting. Both forms wait 5 minutes, a constant. `--no-wait` exists for the stored form. On a timeout a `--code` message is edited to "Timed out" and its button removed, and a stored-form button stays, since a late submit is still useful. An owner message in the thread ends a pending request at once: `request` exits 1 with "owner replied in chat instead" and the message steers the turn as usual. `/stop` kills the child, and the daemon notices the dropped client and edits a `--code` message to "Cancelled".
13. No owner present. A turn a plugin started, and a background task or sub-agent that outlived its turn, count as no owner present. The stored form posts the button with a ping and exits 1 without waiting. `--code` is refused and posts nothing. With `CHAD_SESSION` unset or `daemon`, `request` is refused and points at `chad secret set`. This is a convenience and not a guard.
14. Repeat requests. The daemon remembers each unused button by name and thread, in memory only. A repeat request for the same name in that thread posts nothing: with no owner it exits 1 with "already asked at <time>", and in an owner's turn it waits on the existing button. When a name is saved by any path, every remembered button for it, in every thread, is edited to "Saved NAME". A restart loses the memory, which costs one extra ping, and the button still works because the click is handled from its id.
15. `/secret NAME` and `/secret NAME totp` in chat post the button, and `/secret` alone prints what `chad secret list` prints. It is plain text like `/new`, follows the same mention rule, and never reaches the session. It is the only way to save a secret from a phone when chad is logged out of the model or in safe mode.
16. This replaces "one Stop button and no other buttons or selects" in "What a turn looks like in Discord" (TIM-533). v1 has two buttons, Stop and Enter, and one modal.
17. The modal's field is not masked, because Discord has none. The agent never asks for a password as a message. If the owner pastes one anyway, the agent says it is in the conversation, saves it with `chad secret set` so masking covers what follows, and suggests the owner change it. Changing the password is the fix. `/new` only takes the value out of the live context, because the rows stay for 30 days and are in backups.

Keeping values out:

18. Masking has a floor that is in the spec whatever the prototype finds. chad replaces a stored value of 8 characters or more with `<secret:NAME>` at its own outputs: the history rows it writes, the status message, the log, the `turns` table including `Failed.reason`, everything it posts to chat, and what `afterTurn` hooks receive. It covers script output and script source. TOTP seeds are masked and codes are not. Copies that are URL-encoded, base64 or split are not caught.
19. The better version wraps clanka's `AgentExecutor`, which also keeps the value out of the model's context for the rest of the turn. It ships only if the prototype shows it works with no clanka change.
20. Nothing is scrubbed after the fact. chad does not rewrite rows it already stored.
21. No RPC call returns a stored value. The one exception is `--code`, where the typed code comes back as that call's result and was never stored. `chad secret set` still sends a value to the daemon. The daemon logs no RPC request or response body and no interaction payload.

Where it lives:

22. All of it is CLI commands in the core. The plugin API gains nothing. A second bundled skill, `credentials`, carries the rules and a recipe each for agent-browser and Playwright MCP.
23. What the `credentials` skill has to teach:
    - the quoting trap: `chad secret run --env P=X -- tool "$P"` expands `$P` in the outer shell, so the recipe is `-- sh -c 'tool "$P"'`
    - feeding agent-browser's vault: `chad secret run --stdin GITHUB_PASSWORD -- agent-browser auth save github --url <u> --username <name> --password-stdin`
    - calling `request` with `bash` and `timeoutMs: 330000`, never `run`, which moves it to the background after 2 minutes
    - waiting for the next TOTP window before a retry, since many sites reject a code already used
    - running `auth save` again after a secret changes, because the vault and a browser profile keep their own copy
    - asking for a secret before starting a login, since saving one restarts every MCP server that names it
    - browser state (cookies, saved state files, agent-browser's vault) is a secret: never printed, never sent with `sendFile`, never in the repo
    - where browser state lives. When Playwright MCP launches its own browser its default profile is under the cache directory, which backups skip, so `--user-data-dir` has to point under `home/`. With a sidecar the profile lives in the sidecar, outside `chad backup`.

### What Architect changed

- One-off codes. I had read "enter one-off OTP codes" narrowly, as an ordinary owner message. Architect's reading gives it a command, item 11.
- Masking is not dropped if the clanka seam fails. The floor in item 18 is his.
- Exit 125 for a missing name, and the CLI reading the file itself so no RPC call returns a value.
- 5 minutes in place of 10, because 10 is clanka's bash cap exactly.
- An owner message ending a pending request.
- Items 3, 10 and 14, and browser state in item 23, came from questions I did not ask.

### What this changes in closed tickets

- "What a turn looks like in Discord" (TIM-533): item 16.
- "The chad CLI: what it covers and how it reaches the running daemon" (TIM-542): `chad secret` gains `run`, `code`, `request`, `--totp` and `--note`. "No `get`" still holds and now leans on masking. No RPC call returns a value.
- "Sessions and turns" (TIM-532): `/secret` joins the chat commands, and an owner message ends a pending request before it steers.

### How well each is supported

- Run, from the facts comment: TOTP in 30 lines on `node:crypto` passes the RFC 6238 vectors on Node 26.8.2.
- Read, not run: clanka's bash timeout numbers (`src/AgentTools.ts:271`, `:710-711`, `:901`), the absence of a redaction hook, the `AgentExecutor` seam, Discord's modal rules, and that `ChatTest` supports modals.
- From Architect's memory, checked by nobody: Playwright MCP's `--secrets` takes a dotenv file.
- Not run: every item above. No command exists yet, and no value has been put in a child's environment through chad's spawner.
